# Tauri v2 port

[中文](README.md) · English (translated from the Chinese README, which is the primary version)

> **Status: unofficial, maintained independently.** Upstream [pear-devs/pear-desktop](https://github.com/pear-devs/pear-desktop) has declined to move to Tauri: Tauri relies on the system WebView, whose behavior varies a lot across operating systems and versions (especially troublesome for YTM), and together with the long-term maintenance cost, a smaller binary isn't enough to justify the switch. So this port won't be merged upstream; this fork maintains and releases it on its own. Please report issues here, not upstream.

The Tauri version of Pear Desktop. The page (music.youtube.com) runs the existing renderer (`src/renderer.ts` and each plugin's renderer / preload / menu parts); the work of Electron's main process (config, song info, playback controls, menus, tray, plugin backends) is rewritten in Rust.

How the work is split: **business logic and OS integration live in Rust**; **UI definitions stay in TS** (a plugin's `menu()` template runs in the page and Rust draws it as a native menu; backends that only show translated prompts are also handled in the page, because i18n lives in TS).

## Architecture

```
music.youtube.com page (TS bundle)             Rust (src-tauri/src)
 shim: ipcRenderer ──ipc_send/ipc_invoke──▶  ipc.rs      dispatches by channel to handlers
       listeners  ◀── emit "pear:ipc" ─────    config.rs   owns config.json, plugin watcher
 mainConfig mirror ◀── emit "pear:config" ──    song_info.rs / song_controls.rs / app_controls.rs
 menu-runtime: plugin menu() → JSON ───────▶  menu.rs     native menu (core menu + Plugins)
       click(commandId) ◀── peard:menu-event ─  tray.rs / window.rs / prompt.rs / dialogs.rs
 crossOriginFetch ──── net_fetch (allowlist)─▶  net.rs
                                              plugins/*.rs  plugin backends (Plugin trait)
                                              android_media.rs ──▶ PlaybackService.kt (Android)
```

```
tauri-poc/
├─ inject/                   # page side (bundled into a single IIFE)
│  ├─ entry.ts               # order: shim → plugin-stubs → preload-plugins → menu-runtime → plugin-glue → @/renderer
│  ├─ shim.ts                # window.ipcRenderer / mainConfig / electronIs / __pearCrossOriginFetch
│  ├─ ipc.ts, tauri.ts       # IPC to Rust (no dependency on @tauri-apps/api)
│  ├─ compat/                # build aliases: electron, electron-is, custom-electron-prompt, @/config, @/config/plugins, prompt-options;
│  │                         # discord.ts replaces the main.ts imported by the discord menu (`backendProxies`)
│  ├─ plugin-stubs.ts        # sends the plugin defaults to Rust (plugins_manifest)
│  ├─ preload-plugins.ts     # runs the plugins' preload parts in the page (reuses src/loader/preload.ts)
│  ├─ menu-runtime.ts        # runs plugin menu(), serializes it for Rust, handles clicks; also sends the translations Rust dialogs need
│  ├─ plugin-glue.ts         # UI-only backends (prompts, PiP key, frameless window dragging, like state)
│  └─ crossfade.ts           # crossfade's `audio-url` (youtubei.js runs in the page)
├─ plugin-support.json       # plugins that are forced off (shared by Vite and Rust)
├─ placeholder/prompt.html   # prompt window (replaces custom-electron-prompt)
└─ src-tauri/
   ├─ src/                   # the Rust main process (see the diagram above); menu_mobile.rs is the mobile `menu` (translations only)
   ├─ capabilities/          # ytm-remote.json: the only commands the remote origin may call; prompt.json
   └─ gen/android            # the Android project generated by `tauri android init`; MainActivity, PlaybackService and MediaSessionPlugin are hand-written
```

Matching changes in `src/` and `vite-plugins/` (Electron behavior unaffected): `plugin-loader` can keep several plugin parts at once and exclude given plugins; `virtual:plugins` can emit several `<mode>Plugins()`; new `src/providers/net.ts` (`crossOriginFetch`), which synced-lyrics' LRCLib / Genius / Megalobiz / YTMusic now use; notifications' pure constants moved to `constants.ts`; the scrobbler menu no longer imports the backend; in-app-menu draws its own window buttons when the host sets `__pearNoTitleBarOverlay` (Tauri has no `titleBarOverlay`); do-not-track's pruner no longer calls `delete` on non-objects such as `null` (`JSON.parse('null')` used to throw a TypeError; Electron had this too); song info takes the title YTM shows in the play queue (the player response's `videoDetails.title` can be in another language, e.g. Stefanie Sun's 〈我不難過〉 is "I Am Fine" on a zh-TW page; Electron is affected too); `renderer.ts` resumes its AudioContext on play and on the first interaction (Firefox's autoplay policy leaves it suspended, so videos have no sound), and `pear-trans` is registered with the native `customElements.define` saved when the bundle starts (the ES5 adapter YTM gives Firefox can't construct ES2015 classes); in-app-menu's `titlebar.css` follows the current YTM layout: the sidebar drawer (`[slot=guide]`) and the collapsed mini sidebar (`[slot=mini-guide]`, `#mini-guide-background`) move down by the title bar's height like the nav bar (this relied on `is-bauhaus-sidenav-enabled`, which YTM no longer sets, so the nav bar covered the top of the sidebar and, when collapsed, the Home button), and `ytmusic-app-layout` now fills `100vh` (it subtracted the title bar's height, leaving a 32px gap at the bottom); both problems affected Windows and Android.

### How the code is injected

1. A tiny init script (runs in every frame, but only acts in the top frame) fetches the bundle with a **synchronous XHR** from the custom protocol `pear` (`https://pear.localhost/renderer.js` on Windows/Android, `pear://localhost/renderer.js` on macOS/Linux).
2. It runs it with an indirect `eval` through a Trusted Types policy. YTM's CSP allows `'unsafe-eval'` but requires `require-trusted-types-for 'script'`.
3. This runs at the same time as Electron's preload: before any page script, in the main world.

**Why the bundle isn't simply the init script:** when WebView2 received this 6.6 MB multi-line bundle as an init script, its browser process sat at 100% CPU and the page and DevTools stopped responding. A single-line string of the same size was fine.

### Config

Rust owns `config.json` (`config.rs`, a port of `defaults.ts`). The renderer reads `window.mainConfig.get()` synchronously, so Rust sends a config snapshot in front of the bundle and the page keeps a mirror; every write goes to Rust, which saves it, runs the plugin watcher (on an `enabled` change it sends `plugin:enable`/`plugin:unload` and starts or stops the Rust backend, then sends `config-changed`), and finally broadcasts `pear:config` to update the mirror. Plugin defaults come from the page at startup (`plugins_manifest`); `peard:get-config` waits for them.

### Plugin status

| Status | Plugins |
|---|---|
| Renderer only, worked as is | album-actions, album-color-theme, ambient-mode, clock, equalizer, navigation, performance-improvement, playback-speed, video-toggle, visualizer, etc. |
| Backend ported to Rust | sponsorblock, synced-lyrics (`synced-lyrics:fetch`), lumiastream, tuna-obs, notifications, picture-in-picture, transparent-player, scrobbler, shortcuts (global / in-window shortcuts, media keys), precise-volume, discord, api-server, amuse, in-app-menu, taskbar-mediacontrol (Windows), auth-proxy-adapter (desktop), do-not-track's "With blocklists" mode |
| Backend split between page and Rust | downloader (the page finds the stream, Rust downloads and saves it) |
| Backend handled in the page | captions-selector, quality-changer, music-together (UI only, `plugin-glue.ts`), crossfade (`crossfade.ts`), do-not-track's "In player" mode |
| Unsupported (forced off, greyed out in the menu) | touchbar (see "Platform features this environment can't build or test") |

- **crossfade:** `audio-url` gets the stream URL in the page with youtubei.js (the same approach as `src/plugins/utils/main/youtubei.ts`: a `new Function` interpreter, BotGuard in a hidden iframe, a cached PO token minter; the shared part is `inject/youtubei.ts`); cross-origin requests go through `net_fetch` (the allowlist gained `www.youtube.com` and `jnn-pa.googleapis.com`).
- **downloader:** the page (`inject/downloader.ts`) gets the song info, album, cover and stream URL with youtubei.js (same BotGuard / PO token as crossfade); Rust (`plugins/downloader/`) downloads in 10 MB ranges, writes tags with lofty (title, artist, album, track number, cover; a 1280×720 cover is cropped to 720×720 like Electron) and saves the file as `Artist - Title.m4a`. **There is no ffmpeg. The Tauri default preset is "Source": YouTube's own AAC (`.m4a`)** (Electron's default, mp3 256 kbps, re-encodes the AAC into a file about twice as large that can only sound worse, so `config.rs` changes the default when the plugin defaults arrive; configs that already stored a preset are unaffected). With "mp3 (256kbps)", Symphonia (pure Rust) decodes the AAC and LAME (`mp3lame-encoder`, built from source, LGPL-3.0) encodes a constant-bitrate mp3, then ID3v2 tags and the cover are written (`plugins/downloader/mp3.rs`); conversion progress shows on the download button. "Custom" only supports the mp3 extension with a `-b:a` bitrate; anything else saves the source file. The presets menu explains this at the top. When cross-compiling LAME for Android on Windows, `mp3lame-sys` uses the MSVC config.h, which clashes with the NDK's `<stdint.h>`; `src-tauri/.cargo/config.toml` force-includes `build-support/include/pear-stdint-first.h` for Android targets to fix it. Dev builds also optimize these codec crates (a 3.5-minute song goes from about 15 s to about 4 s). YouTube serves fragmented (DASH) MP4, which Windows' built-in player opens but doesn't play (it jumps to the end), so the file is rewritten as a regular MP4 before tagging (`plugins/downloader/remux.rs`, the equivalent of ffmpeg's `-c copy`; yt-dlp does this step too). Single songs are downloaded from the top of each song's "⋮" menu (the "Download" the plugin adds, not YTM's own Premium download with the P badge). Playlists, albums (track numbers), skipping existing files, download on finish, the taskbar progress bar, and the error and download-started dialogs match Electron. youtubei.js uses a signed-out session (like crossfade), so Premium's 256 kbps format, age-restricted songs and private playlists (e.g. "Liked Music") can't be downloaded. **Android:** files go to the shared "Music/Pear Desktop" (MediaStore, no permission needed on Android 10+; on Android 8 and 9 they go to the app's own music folder, which is removed with the app), and the folder items are hidden from the menu. The menu runs in the page; `compat/downloader-menu.ts` wraps the original menu: folder pickers use the async dialog (`pear:show-open-dialog` gained `openDirectory`), and `main/index.ts` and `main/utils.ts` are replaced by `compat/downloader.ts`.
- **proxy and auth-proxy-adapter:** Options › Advanced gained "Set proxy" (`options.proxy`, Electron's `--proxy-server`); it takes effect after a restart. Windows applies it when WebView2 starts, and Rust's own requests (lyrics, covers, downloads, etc.) use the same proxy; Chromium can't pass SOCKS credentials, so with auth-proxy-adapter on, WebView2 connects to the local SOCKS5 relay it opens (`plugins/auth_proxy_adapter.rs`), which carries the credentials to the upstream proxy. **Android (GeckoView)** applies it directly in the pear-gecko extension's `browser.proxy.onRequest`, SOCKS credentials included, with immediate effect and no relay.
- **discord:** Rust speaks Discord's local IPC directly (Windows named pipe `discord-ipc-N`, Unix socket), replacing `@xhayper/discord-rpc`; throttling, clearing after a long pause and auto-reconnect follow `DiscordService`. The menu runs in the page; the `main.ts` it imports is replaced at build time by `compat/discord.ts` (reads the connection status, connects and clears over IPC).
- **api-server:** rewritten on axum; routes, JWT (HS256, compatible with hono/jwt), CORS and WebSocket events match the Electron version; the `AUTH_AT_FIRST` Allow/Deny dialog uses translations sent by the page. `/doc` (OpenAPI) and `/swagger` come from the zod route definitions, which Rust can't run, so a build step generates them (`scripts/api-openapi.mts` loads the real route modules in Vite SSR with the main-process modules stubbed, registers them like `backend/main.ts`, and takes Hono's responses); Rust serves them as they are, and Swagger UI loads from jsDelivr like Electron's. The default secret is `Date.now()` at page load; Rust saves it to the config on first launch so tokens survive a reload. HTTPS uses rustls (ring).
- **amuse:** `/`, `/query` and `/api` on port 9863, on axum.
- **in-app-menu:** when enabled (the Windows default) the main window is frameless and the page draws the menu and window buttons; Rust answers `get-menu` / `peard:menu-event` / `window-*`. `plugin-glue.ts` turns `app-region: drag` into `start_dragging` (double-click maximizes). The window-state plugin doesn't restore decorations / visibility, which would override this setting. On Android it is the only menu: it is always on at startup, and its switch under Plugins is greyed out so it can't be turned off (once off, only adb could change the setting back) (the page's UA-based default is off on "Linux"); it draws no window buttons (`__pearNoWindowControls`), and the menu drops items Android can't use (always on top, start at login, tray, zoom, full screen, DevTools, custom window title, restart / quit).
- **System media controls:** on Windows, WebView2 provides SMTC itself (shown as `msedgewebview2.exe` or "Unknown app", and setting an AppUserModelID doesn't change that); taskbar-mediacontrol's thumbnail buttons use `ITaskbarList3`. Linux MPRIS and macOS Now Playing are not ported (see "Platform features this environment can't build or test"). For Android see "Background playback" below.
- **notifications:** with `interactive` on, Windows shows a WinRT toast with previous / play-pause / next buttons in all seven `toastStyle`s (`plugins/notifications/toast.rs`, a port of `interactive.ts`). The buttons are handled in-process through the toast's own `Activated` event (Electron used the `peard://` protocol, which starts a second instance), so the app has to be running. The buttons have text (the tray menu's translations, hidden when `hideButtonText` is on; Electron's check tested `toastStyle` instead, so its text never showed) and icons, black or white to match Windows' light or dark theme (Electron always used black, invisible on a dark theme). Like Electron, the toast hides after 5 seconds, `refreshOnPlayPause` shows it again, and `trayControls` makes a tray click show or hide the toast (double-click toggles the window). Differences from Electron: titles are XML-escaped (Electron's toast fails on `&`), each song's cover gets its own file name (Windows caches toast images by path), and switching modes needs no restart. Unpackaged dev builds (`target\debug`) have no registered AppUserModelID, so toasts show as PowerShell's, as with tauri-plugin-notification; installed builds use the app identifier. Registering the dev build's own ID under `HKCU\Software\Classes\AppUserModelId\` (display name and icon) was tried: Windows accepted the toasts but never showed them (adding `CustomActivator` didn't help), so dev builds keep PowerShell's ID; showing the app name in dev builds would need a Start menu shortcut carrying the AppUserModelID, as installers create. Other platforms, and `interactive` off, use the basic notification.
- **do-not-track (ad blocking):** the default **In player** mode runs entirely in the page (wraps `JSON.parse` and `Response.json` and deletes `playerAds` / `adPlacements` / `adSlots` from player responses) and works on Windows and Android. The **With blocklists** mode uses Brave's adblock-rust (`plugins/do_not_track.rs`) with the same lists as Electron (the default lists from tb.json unless `disableDefaultLists`, plus `additionalBlockLists`), and Ghostery's copy of uBlock Origin's resources for scriptlets and redirects; with `cache` on and no additional lists the engine is cached (and, like Electron, never refreshed automatically). Only the default lists may use `trusted-*` scriptlets. **Windows** checks every request of the main webview in `WebResourceRequested` (including service workers and iframes); blocked requests get an empty 403 and redirects get their resource; the app's own `*.localhost` is never checked. **Android:** the pear-gecko extension's `webRequest` (blocking) asks Rust over native messaging (`dnt_check`). On both, the page asks Rust for the URL's hiding CSS (one rule per selector, so a selector the browser rejects only drops its own rule) and scriptlets where Electron loaded the Ghostery preload. Not ported: the generic class/id hiding the Ghostery preload computes from the DOM, procedural filters and `removeparam`. Unlike Electron, the engine is unloaded when switching back to In player (Electron only does so when the plugin is turned off). At build time `blocker.ts` and the Ghostery preload are replaced by `compat/do-not-track.ts`.
- **Player events requested on start:** Electron's backends only request `peard:setup-*-listener` on `peard:player-api-loaded`, which a plugin enabled while running misses; the Rust version (`plugins::request_player_listeners`) also requests them right away when it starts (the page side is a singleton, so asking twice is harmless).

**CSS:** the renderer's `import 'mdui/mdui.css'` is extracted by Vite into a separate CSS file, but Electron's `get-renderer-script` only reads the `<script>`, so that CSS was never applied in Electron. The PoC once inlined it, and mdui's `:root { background-color }` painted grey patches behind YTM's translucent backgrounds; it is now dropped, matching Electron.

### Platform features this environment can't build or test

The PoC is only built and tested on Windows and Android. These features need Linux or macOS and are not implemented; only porting notes are kept:

- **Linux MPRIS (the shortcuts plugin's media controls):** the Electron version is `src/plugins/shortcuts/mpris.ts`. Rust could use zbus (already in the lockfile as a Tauri dependency) to register `org.mpris.MediaPlayer2.*` on the session bus, mapping properties and methods to `song_info` (Metadata, PlaybackStatus, Position) and `song_controls` (Play, Pause, Next, Previous, Seek, Volume, Shuffle, LoopStatus), with the `Seeked` signal driven by `peard:seeked`. Whether WebKitGTK registers its own MPRIS player needs testing, to avoid two players.
- **macOS Now Playing:** objc2-media-player's `MPNowPlayingInfoCenter` (title, artist, album, cover, duration, current time, playback rate) and `MPRemoteCommandCenter` (play, pause, previous, next, seeking). WKWebView may report media info as well; that needs testing too.
- **Touch Bar (the touchbar plugin):** unsupported. Tauri has no Touch Bar API and Apple has discontinued the Macs that had one; `plugin-support.json` keeps it forced off.

### Electron options not ported yet

Apart from "Set proxy", these Electron options are not ported (they don't appear in the menu): user-agent override (`overrideUserAgent`), disable hardware acceleration (`disableHardwareAcceleration`), reset the cache on start (`autoResetAppCache`), hide the menu bar (`hideMenu`), the single-instance toggle (the PoC is always single-instance), custom theme CSS (`themes`), and auto-update (`autoUpdates`; not planned for the PoC).

### Pitfalls met while porting

- **Electron's Chromium switches have to reach WebView2 too.** Electron enables `OverlayScrollbar` and disables `FluentScrollbar` (`src/index.ts`), so scrollbars float over content and take no width; WebView2 defaults to classic scrollbars, so a song menu or an in-app-menu panel taller than the window got a wide scrollbar plus a horizontal one, because the vertical one took width. `window.rs` starts WebView2 with the same switches on Windows. Setting browser arguments replaces wry's defaults (so they are repeated first) and makes wry ignore `proxy_url`, so the proxy is passed as an argument too (without credentials; auth-proxy-adapter's relay carries those).
- **`shim.ts` must not import `virtual:plugins`.** It loads every plugin statically, so plugin top-level code runs before the shim defines the globals and throws `Cannot read properties of undefined (reading 'on')`.
- **The page bundle must not import main-process code.** If a menu or preload indirectly imports `node:*` or calls Electron's `app` at load time, the whole bundle crashes in the page. So unported plugins have their menu/preload excluded via `plugin-support.json`, and ported ones are split up in `src/` (e.g. notifications' `constants.ts`).
- **All webviews need the same WebView2 environment options.** Prompt windows, the Last.fm login window and the main window must all use the same `use_https_scheme` and browser arguments (`window::shared_webview_options`), or creating them fails (HRESULT `0x8007139F`).
- **Set the menu on the main window, not with `app.set_menu`.** An app-level menu is attached to prompt windows too, and closing a prompt tears the shared menu down.
- **Don't call tray / window APIs synchronously off the main thread.** Song info callbacks run on async workers; calling `tray.set_icon` directly waits for the main thread and can deadlock. Schedule it with `run_on_main_thread`.
- **Don't hold a lock while calling window APIs.** `set_position` / `set_size` fire window events synchronously on the same thread; if the event handler takes the same lock, it deadlocks (PiP once froze the whole app this way).
- **HTML full screen becomes window full screen.** The Tauri runtime turns the page's fullscreen straight into window fullscreen, with no equivalent of Electron's `setFullScreenable(false)`; PiP undoes it in the Resized event.
- **`set_size` sets the inner size.** To restore a size, save `inner_size()`; saving `outer_size()` adds the frame and menu bar height every time.
- **Menu item methods also wait for the main thread.** Calling `CheckMenuItem::is_checked()` on a worker while holding the `checks` lock, while the main thread rebuilds the menu and wants the same lock → the whole app hangs (hit when refreshing the menu after discord connected). Items are now always cloned out of the lock before calling them.
- **Main-process code has to compile for mobile.** Menus, tray, prompt windows and window operations don't exist on Android; those modules and functions are fenced with `cfg(desktop)`. `menu.rs` is shared: the menu tree (Electron-format JSON for in-app-menu) and click handling are the same, native menu items are only created on desktop, and on Android check states live in `CheckItem`.

## Running (Windows)

From the repository root (Node 26 no longer bundles corepack; if `pnpm` points to a broken corepack shim in `C:\Program Files\nodejs`, use a standalone pnpm 11):

```bash
pnpm exec vite build -c tauri-poc/vite.inject.config.mts
```

```bash
cargo run --manifest-path tauri-poc/src-tauri/Cargo.toml
```

| Environment variable | Effect |
|---|---|
| `PEAR_POC_DEVTOOLS=1` | Opens DevTools on start (look for `[pear-tauri]` logs) |
| `PEAR_POC_USER_AGENT=...` | Overrides the User-Agent (e.g. to test when Google sign-in is blocked) |
| `PEAR_POC_NO_INJECT=1` | No injection; loads the plain site (to tell shell problems from renderer problems) |
| `PEAR_POC_INJECT_FILE=path` | Injects a file from disk instead, no rebuild needed |
| `PEAR_POC_PROFILE_DIR=path` | Keeps the WebView data and `config.json` in this folder (e.g. to test signed out without touching the real login) |
| `PEAR_POC_DEBUG_PORT=9333` | Opens the Chrome DevTools Protocol (keeps Tauri's default WebView2 arguments; don't use `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` instead, it replaces the defaults entirely) |

Close the window normally when testing. Killing the process gives WebView2 no time to write cookies back, and the login is lost; if the main process has stopped responding, use CDP's `Browser.close` to close WebView2 cleanly before ending the process. Also, pressing Alt on its own puts the window in Windows' menu mode, during which WebView2 (DevTools at least) stops responding; press Esc to leave it.

Rust unit tests: `cargo test --manifest-path tauri-poc/src-tauri/Cargo.toml --lib` (song info parsing, config merging, SponsorBlock segment merging, Last.fm signatures, shortcut name conversion, the `net_fetch` allowlist, etc.).

## Running (Android)

Needs a JDK (the JBR bundled with Android Studio will do) and the NDK:

```bash
export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr" NDK_HOME="$LOCALAPPDATA/Android/Sdk/ndk/28.0.13004108"
```

```bash
cd tauri-poc/src-tauri && pnpm dlx @tauri-apps/cli@2.12.4 android build --debug --apk --target x86_64
```

- `gen/android/gradle.properties` sets `android.overridePathCheck=true`, because the repository path contains Chinese characters (`D:\程式專案`) and AGP refuses to build by default.
- If the emulator shows `ERR_NAME_NOT_RESOLVED` (common when the host runs a VPN such as Tailscale), start it with `emulator -avd <name> -dns-server 8.8.8.8`.
- `MainActivity` presents the WebView as **desktop Chrome of the same version**: the UA string uses the actual WebView version, and Client Hints (`Sec-CH-UA*`, `navigator.userAgentData`, which listed "Android WebView") are changed to Google Chrome / Linux / not mobile with `WebSettingsCompat.setUserAgentMetadata`. Otherwise the mobile YTM is served (plugins don't work there) and Google sign-in refuses with "This browser or app may not be secure". The `X-Requested-With: <package name>` header is still sent: `setRequestedWithHeaderOriginAllowList`, which would turn it off, isn't supported on WebView 143 (`REQUESTED_WITH_HEADER_ALLOW_LIST` is false).
- From Android 15 the screen is forced to extend under the system bars; `MainActivity` pads by the system bar and cutout insets, with YTM's `#030303` as the background and light system bar icons.
- **YouTube Music links:** the manifest declares a VIEW intent filter for `https://music.youtube.com`, and `MainActivity` loads the received link (on a cold start after wry's start URL, while running through `onNewIntent`). The app can't pass verification for that domain, so from Android 12 it doesn't take over automatically: add `music.youtube.com` under "App info › Open by default"; if the official YouTube Music app is installed, it is the verified handler and wins. The official app is often preinstalled and can't be removed (confirmed on a device); the steps are:
  1. Settings › Apps › YouTube Music › Open by default: turn off "Open supported links" (or untick `music.youtube.com`).
  2. Settings › Apps › Pear Tauri › Open by default: "Add link" and tick `music.youtube.com`.

  After that, `music.youtube.com` links open in Pear (confirmed on a device). The desktop version has no equivalent (Windows can't register a handler for https URLs).
- **Google sign-in:** not possible in WebView, and the PoC won't work around it. The POSTs the sign-in page itself sends (`AccountsSignInUi/data/batchexecute`, `browserinfo`) all carry `X-Requested-With`, and `shouldInterceptRequest` can't read POST bodies, so they can't be resent without the header; `browserinfo` also returns a browser fingerprint. The WebView version can only be used signed out; the way forward is GeckoView (see the next section).
- On a real tablet use `--target aarch64` instead.
- **Page engine:** GeckoView by default (Google sign-in works, see "GeckoView feasibility check"). `adb shell am start -n io.github.junxiangzhan.peartauri/.MainActivity --es engine webview` switches back to WebView and `--es engine gecko` back again; the choice is remembered. `MainActivity` writes it to the `PEAR_ENGINE` environment variable before Rust starts (read by `src/page.rs`). The WebView notes below apply only to the WebView engine.
- **GeckoView viewport:** the UA is desktop Firefox (plugins need the desktop site), but the viewport uses `VIEWPORT_MODE_MOBILE`, laying out by YTM's own `<meta name="viewport" content="width=device-width">` like WebView. `VIEWPORT_MODE_DESKTOP` lays the page out at least 980 CSS px wide, so a smaller window (split screen, floating window, phone) never switches to YTM's narrow layout; a tablet floating window (381 dp) measured a 385 px viewport.
- **Floating windows:** when this MIUI tablet turns the app into a floating window, it first gives it a phone-sized window (420×750 dp), and after about 0.5 s switches to **a full tablet-sized window shown scaled down** (logcat's `mFreeFormScale=0.526`; the configuration returns to 1164×777 dp). So the floating window shows a scaled-down tablet layout and can't be resized back to phone proportions: this is how MIUI does floating windows for this app, not an app limitation (opened with `am start --windowingMode 5` it can be phone-shaped, and the page switches to the narrow layout).
- **Layout stuck in the narrow mode after a floating window (fixed):** missing player page elements and a second YouTube Music logo in the sidebar are both YTM bugs: it tracks the layout size class (-4 to 3) with media queries and applies it with checks like `size && size >= -1` (persistent sidebar) and `size && size >= -2` (showing the nav bar and player bar while the player page is open), and class 0 (1150–1363 px wide; this tablet is exactly 1173 px) is falsy, so **jumping straight into class 0** from a narrow layout updates nothing and the layout stays narrow (nav bar and player bar `visibility: hidden`, the sidebar left as the narrow layout's overlay drawer and header). Dragging a window passes through class -1, so it usually doesn't show; the MIUI floating window jumps in one go. Electron should hit it too when maximizing a narrow window straight to this width. `inject/shim.ts` wraps `MediaQueryList.addListener`: when the class 0 query starts matching, it first reports class -1 to YTM's listeners and only sends class 0 100 ms later, like a drag passing through -1. Verified with `am task resize` (load phone-sized → tablet → phone → tablet): the sidebar is persistent, the header hidden, the nav bar and player bar shown, and shrinking back hides them the way YTM normally does. `MainActivity` logs configuration changes to logcat (tag `PearMainActivity`), and `report.js` records recent window sizes, devicePixelRatio and changes to these media queries.
- **Full screen:** the Android "View" menu has a "Toggle full screen" check item that hides the status bar and navigation bar (three buttons or the gesture hint); swiping from an edge shows them for a moment. The choice is kept in `options.fullscreen` and used on the next start (`src/android_app.rs`, `AndroidAppPlugin.kt`).
- **The init script runs twice:** wry's generated Android code injects the init script with `addDocumentStartJavaScript`, but `RustWebViewClient.onPageStarted` also runs `evaluateJavascript` for every page Rust didn't intercept, without checking whether the former is available (a wry bug; `generated/` is regenerated on every build, so it can't be edited). The PoC's loader uses `window.__pearRendererLoaded` to load the bundle only once per document; Tauri's own scripts still run twice, and the console shows a harmless `Cannot redefine property`.
- **Known issue:** occasionally the page stays blank (`about:blank`) after start; force-stopping and reopening fixes it. Not investigated yet.
- A debug APK with full debug info is about 374 MB (`.so` 240 MB) and may not install on an emulator short of space; for testing, set `CARGO_PROFILE_DEV_DEBUG=0 CARGO_PROFILE_DEV_STRIP=debuginfo` before building (about 134 MB).

### Background playback

- `PlaybackService` (a `mediaPlayback` foreground service + `MediaSession`) keeps Android from freezing the process and provides the system media controls (notification, lock screen, media keys). `android_media.rs` sends the song info through Tauri's Android plugin (`MediaSessionPlugin`); buttons come back to Rust over a Channel as `song_controls`. The once-per-second time updates are only forwarded on seeks (a difference of over 2 seconds); otherwise `PlaybackState` extrapolates.
- **A foreground service alone isn't enough:** when the WebView gets `onPause()` (which `WryActivity` calls) or the window becomes invisible, Chromium pauses media with a video track, and YTM always plays through `<video>`. While the service runs, `MainActivity` calls `webView.onResume()` right after `onPause`, and reports the window visibility back as `VISIBLE` after `onStop`.
- The notification stays put while paused (the service doesn't leave the foreground), to avoid Android 12's "no foreground service from the background" restriction when playback resumes from the background later. Swiping the app away from recents stops the service (the WebView goes with the activity).

  ```bash
  keytool -genkeypair -keystore pear-release.jks -alias pear -keyalg RSA -keysize 4096 -validity 10000
  ```

  ```bash
  base64 -w0 pear-release.jks | gh secret set ANDROID_KEYSTORE_BASE64 --repo junxiangzhan/pear-desktop
  ```

  ```bash
  gh secret set ANDROID_KEY_ALIAS --body pear --repo junxiangzhan/pear-desktop
  ```

  ```bash
  gh secret set ANDROID_KEYSTORE_PASSWORD --repo junxiangzhan/pear-desktop
  ```

  ```bash
  gh secret set ANDROID_KEY_PASSWORD --repo junxiangzhan/pear-desktop
  ```

### The cause of the stutter: performance-improvement's cpu-tamer

`src/plugins/performance-improvement/scripts/cpu-tamer/cpu-tamer-by-animationframe.js` inserts a hidden `<a-f>` element running a 1 ms infinite CSS animation, uses its `animationiteration` event as a clock (fired every frame), and rewrites the global `setTimeout`/`setInterval`: while media plays, YTM's timers are deferred to the next clock tick. On a high-refresh display (e.g. 165 Hz) the main thread is woken every frame, so scrolling drops frames and feels like "move, stall, move", easily mistaken for GC.

**Fixed** ([pear-devs/pear-desktop#4772](https://github.com/pear-devs/pear-desktop/pull/4772), merged into `master`): the clock uses `requestAnimationFrame` and only requests the next frame while timers are waiting. Timer deferral and coalescing are unchanged (a 1 ms `setInterval` still fires about 164 times a second while playing). So the PoC no longer turns this plugin off by default.

Re-measured in the PoC after the fix (Windows, WebView2, signed in, not playing, 165 Hz, 1100×700 window on top; the same simulated wheel as Electron: 120 px every 33 ms, reversing every 2 seconds; each case 15 s × 2, averaged; bundles switched with `PEAR_POC_INJECT_FILE`):

| Simulated scrolling: dropped frames | 64 | 684 | 73 |
| Simulated scrolling: main thread busy | 62.9% | 87.3% | 60.3% |
| Idle: main thread busy | 4.3% | 33.0% | 4.3% |

- **Background playback stopping, three causes** (GeckoView's config file `files/geckoview-config.yaml`, written by `GeckoPage` at startup):
  1. When the app goes to the background, Gecko lowers the utility and GPU processes to IDLE priority, and the phone kills them within about 30 seconds; the audio or video decoders go with them, and YTM resets the player. Setting `media.utility-process.enabled: false` and `layers.gpu-process.enabled: false` moves decoding into processes that aren't killed (the content process playing audio, and the main process with `PlaybackService`).
  2. The renderer routes video through an AudioContext, and Gecko's autoplay policy leaves an AudioContext created without a user gesture suspended, so **the output is silent** (when the app resumes playback by itself, there's no sound until the first tap). HyperOS's PowerKeeper pauses a background app's audio after 60 seconds of continuous silent output (logcat: `isLongTimeZeroData out of time 60S`, `pause zero data process`), and playback stops where it is. Setting `media.autoplay.default: 0` (Web Audio included) makes the AudioContext running as soon as it's created.
